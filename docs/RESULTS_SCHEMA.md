# Results schema

Every run leaves a self-contained directory: raw logs and series, one `run.json` with provenance and status, and a
`metrics.json` that `bbench analyze` recomputes from the raw files. The JSON schemas live in [`schemas/`](../schemas/);
`bbench validate <path>...` checks files against them.

## Layout

```
runs/<matrix>/
  <run_id>/
    run.json                 provenance, config, marks, overrides, interventions, spread, status
                             (run.partial.json while the run is in progress)
    metrics.json             computed metrics; regenerated by `bbench analyze`
    server.log.gz            server console output
    commands.jsonl.gz        every console write
    bots.jsonl.gz            raw bot events
    series/
      probe.csv              tick probe replies
      threads.csv.gz         per-thread CPU, 1 Hz
      tick.csv.gz            tick-thread CPU, 10 Hz
      process.csv.gz         process and tree CPU and memory, 1 Hz
      machine.csv.gz         per-CPU busy and foreign load, 1 Hz
      foreign_top.jsonl      busiest foreign processes, every 10 s
    chaos-plan.jsonl         chaos scenarios: the pre-generated plan
    chaos-exec.jsonl         chaos scenarios: scheduled, sent and applied time of every action
    config/                  rendered configs as written, and as found after shutdown
    crash/                   last log lines and crash files, if the server died or exited nonzero
  summary.json               aggregate over repeats
  report.md                  the rendered report
```

The run id is `<UTC yyyymmddThhmmssZ>-<arm>-<scenario>-r<repeat>-<4 hex>`, for example
`20261012T135800Z-endstone@0.11.14-spread100-r1-3fa2`. Existing run directories are never overwritten or deleted.

## Time

All harness timestamps are monotonic nanoseconds (`*_ns`) from one clock, taken when the harness reads the data, not
when it asks for it. `run.json` stores one origin pair, `time.origin_mono_ns` and `time.origin_epoch_ms`, taken together
at the start of the run. Sources stamped with wall-clock time (bot events carry `t` in epoch milliseconds) are mapped
onto the monotonic timeline through that pair; `time.drift_ms` records how far the two clocks drifted during the run.
Phase marks in `run.json` are seconds since the origin.

## Raw files

| File | Format |
|---|---|
| `server.log.gz` | one line per console line: `<mono_ns>\t<epoch_ms>\t<line>`, ANSI escapes stripped, invalid UTF-8 replaced |
| `commands.jsonl.gz` | one JSON object per console write: enqueue and send time, lane (`normal` or `priority`), origin (`phase`, `probe` or `chaos`), text |
| `bots.jsonl.gz` | every bot event as emitted ([bot events](#bot-events)), plus `rx_ns`, the harness time it was read |
| `series/probe.csv` | `send_ns,rx_ns,tick` |
| `series/threads.csv.gz` | `t_ns,tid,name,cpu_ns[,cycles]` |
| `series/tick.csv.gz` | `t_ns,cpu_ns` |
| `series/process.csv.gz` | `t_ns,user_s,sys_s,resident_mib,private_mib,threads,handles,tree_user_s,tree_sys_s` |
| `series/machine.csv.gz` | `t_ns,foreign_cores,foreign_server_set_cores,cpu0..cpuN` |
| `series/foreign_top.jsonl` | one object every 10 s with the busiest foreign processes (name and cores) |

Memory is in MiB (2^20 bytes). Reports convert to GiB by dividing by 1024.

## `run.json` (`bedrock-bench/run/1`)

| Section | Content |
|---|---|
| `schema`, `schema_minor`, `analysis_version` | versions (below) |
| `run_id`, `status`, `status_reasons`, `flags`, `exit_code` | outcome; `status` is `ok`, `server_failed` or `invalid` |
| `official`, `nonstandard` | whether the run used only released artifacts and standard settings, and what was not |
| `harness` | harness version, git describe, dirty flag, Python version, backend (`native-windows`, `native-linux`, `docker-linux`) |
| `matrix` | matrix name, repeat, position in the run order, order mode |
| `arm` | id (`<server>@<version>`, plus `+<variant>`), server, version, variant, hosted BDS version, Python version, local artifact |
| `artifacts` | every downloaded file: name, url, sha256, size, source (`mojang`, `pypi`, `github`, ...) |
| `install` | hash of the installed tree; for BDS-hosted servers the executable's sha256 before and after the run |
| `server` | pid, launcher pids, banner version, facts (allocator, JVM heap, thread census at idle, effective client-side generation setting) |
| `overrides` | every config change: category, file, key, default, value, reason |
| `config_files` | sha256 of each config as written and as found after shutdown |
| `parity` | feature file hash, matching version range, declared class per feature, fidelity, "does less" list |
| `bot` | module, protocol, binary sha256, Go and gophertunnel versions, patches, argv |
| `scenario` | name, sha256, fully resolved content |
| `machine` | fingerprint id, label, OS, kernel, CPU model, logical and physical CPUs, core classes, RAM, virtualisation, power plan, calibrated TSC, profile hash |
| `placement` | server, bot and harness CPUs, priority, kind (`physical` or `vcpu`), method, verified |
| `time` | origin pair, end pair, drift |
| `world` | fresh or template, generator (`vanilla`, `custom`, `flat`), template sha256 |
| `marks` | `ready`, `idle0`, `idle1`, `bots_start`, `alljoined`, `settled`, `steady0`, `steady1`, `chaos0`, `chaos1`, `stop`; null when not reached |
| `settle` | duration, capped, views incomplete |
| `interventions` | nudges and re-teleports with the bots they hit; interventions inside measured windows |
| `spread` | position source, players, cells occupied, max per cell, worst offset |
| `health` | died, exit code, crash files, joined, failed, dropped, decode errors |
| `interference` | idle foreign load and, per window, foreign load, 10 s peak, load on the server's CPUs, harness cores, top foreign processes |
| `files` | sha256 and size of every raw file in the run directory |

`run.partial.json` has the same shape with `partial: true` and `status: null`; it is rewritten after every phase and
replaced by `run.json` at the end.

**Privacy.** `run.json` stores no hostname, username or absolute path. Paths are relative to the run or server
directory, and the machine is identified by a fingerprint id and a label you choose. The harness scrubs every string
before writing and a test checks it. Raw logs are the server's own output; check them before sharing.

## `metrics.json` (`bedrock-bench/metrics/1`)

```json
{
  "schema": "bedrock-bench/metrics/1",
  "schema_minor": 0,
  "analysis_version": 1,
  "run_id": "20261012T135800Z-endstone@0.11.14-spread100-r1-3fa2",
  "status": "ok",
  "status_reasons": [],
  "flags": [],
  "metrics": {
    "tps_window_steady": {"value": 19.98, "unit": "tps", "window": "steady", "n": 19, "availability": "measured"},
    "mspt_saturated_steady": {"value": null, "unit": "ms", "window": "steady", "n": null,
                              "availability": "not_applicable", "reason": "tps_window >= 19.5"}
  },
  "tables": {"threads_top_steady": [], "pkt_mix_steady": []}
}
```

Each metric has a `value` (a number, a censored value or a small object such as min/median/max), its `unit`, the
`window` it covers, the sample count `n`, and an `availability`:

- `measured`: the value exists;
- `not_applicable`: the server or scenario has no such quantity (the tick thread of a Go server, chaos metrics in a
  non-chaos run);
- `unavailable`: the value should exist but could not be computed; `reason` says why.

`tables` holds diagnostic and work tables: top threads, packet mix, chaos regimes and similar. Metric ids, units and
formulas are listed in [METRICS.md](METRICS.md), generated from the registry in the code.

`bbench analyze <run_dir>` recomputes `metrics.json` and the status from the raw files. With the same
`analysis_version`, the output is identical byte for byte; a golden test checks this on stored fixture runs.

## `summary.json` and `report.md`

`bbench report <matrix_dir>` aggregates the runs of a matrix directory. For every arm, scenario and metric,
`summary.json` holds the median, minimum, maximum and every value of the `ok` runs, plus `n_ok` and `n_total`.
`server_failed` runs count in `n_total` and the status column, never in a median. `report.md` renders the conditions
block, parity rows, cost and work tables and footnotes ([READING.md](READING.md)). `--claims` adds the result of each
relational claim (`claims/*.toml`, `schemas/claims.schema.json`).

## Bot events

The bot writes one JSON object per line (`schemas/bot-event.schema.json`, `v = 1`). Every line has `v`, `ev`, `t` (epoch
milliseconds, UTC) and `mono_ms` (the bot's monotonic clock since it started).

| Event | Content |
|---|---|
| `hello` | bot build (module, version, VCS, Go, gophertunnel, patches, protocol), flags, reporting intervals |
| `dial`, `spawned`, `join_failed` | per-bot join lifecycle; `spawned` carries `join_ms`, the session and the granted radius; `join_failed` the stage (`dial`, `login`, `spawn`) |
| `tp` | a confirmed teleport with position and dimension |
| `first_chunk` | time from teleport to the first in-view chunk |
| `progress` | every 5 s, one row per bot: unique chunks, in-view chunks, position, dimension, corrections, teleports |
| `stat` | every 10 s, cumulative fleet counters: online, joined, failed, dropped, rejoins, deaths, packets and bytes, corrections, chunks, decode errors |
| `pkt` | every 60 s, received packet counts by type since the last `pkt` |
| `rtt` | latency probe statistics, when enabled |
| `died`, `respawned`, `dim`, `left`, `dropped`, `rejoin`, `kicked` | lifecycle events |
| `decode_error` | a packet the bot could not decode (rate-limited, with a running total) |
| `alljoined` | every bot has joined or failed |
| `bot_summary` | per bot at the end: chunk counts, corrections, first-seen times of in-view chunks (delta-encoded ms since the first teleport) |
| `done` | the bot exited cleanly |

## Versioning

- **Schema.** `schema` names the major version (`bedrock-bench/run/1`); `schema_minor` counts additive changes such as
  a new optional field or enum value. Removing, renaming or redefining a field bumps the major version: the old schema
  file stays next to the new one, and the harness migrates old runs when it loads them.
- **Analysis.** `analysis_version` changes whenever a metric formula changes. Runs analysed with different versions are
  not compared; re-run `bbench analyze` to bring old runs up to date.
- **Scenario.** `scenario.sha256` covers the fully resolved scenario. Runs with different hashes are different
  workloads.
- **Harness.** `harness.version` and `harness.git` identify the code that ran; `harness.dirty` is true when the checkout
  had uncommitted changes. Publications require a clean checkout.
